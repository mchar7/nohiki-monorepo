# BFF Service Database Design

Schema `bff_schema` is the BFF's local read-model database. Domain data is owned by upstream services; the BFF keeps
denormalized, eventually consistent projections populated by Kafka CDC or fact-event handlers. API routers read those
projections, while projection writes remain confined to the event handlers. Associations preserve upstream service
identities and are coordinated through events rather than synchronous cross-service data access.

The exceptions are the BFF's locally owned records for asynchronous document generation and command progress. They track
request lifecycles but do not make the BFF authoritative for the domain entities affected by those requests.

## Projection ownership and lifecycle

### Accounts

Account state is projected from `user-auth-service` through `USER_AUTH_ACCOUNT_UPDATED`. It gives the BFF account
metadata beyond the JWT for `/api/v1/session`-adjacent workflows, with production reads keyed by the canonical user
identity carried in the JWT `sub` claim.

The projection retains the upstream mutation time rather than substituting the local projection arrival time. Before
applying a snapshot, the handler removes a stale projection that has the same email under a different identity; this
preserves identity consistency when an address is re-registered. Updates apply the current snapshot, and
`USER_AUTH_ACCOUNT_DELETED` removes the projection.

### Search preferences and user settings

Search preference projections mirror `SearchPref` entities from `user-pref-service`. Search keywords feed
`job-query-composition-service`, disallowed keywords can reject listings from matching, and the auto-tailor threshold
determines when document tailoring starts automatically. Work-arrangement, notification, feature-importance, and commute
choices drive matching and notification behavior. The BFF reads these projections for `GET /api/v1/profiles`, per-user
profile lists, and feature-importance resolution.

Percentage thresholds from the upstream snapshots are converted to ratios at projection time. Commute preferences are
carried from their protobuf snapshot representation. A repeated `USER_PREF_CREATED` is ignored, while
`USER_PREF_UPDATED` replaces the mutable snapshot state and `USER_PREF_DELETED` removes it.

User preference settings provide at most one set of global feature-importance defaults per user. Resolution prefers a
profile-specific override, then the user's defaults, then system defaults of 50 for every dimension. Repeated
settings-create events are ignored, and settings-update events replace the projection associated with that user.

### Attachments

Attachment metadata is projected from `user-upload-service` for the `/api/v1/attachments` endpoints.
`USER_UPLOAD_CREATED` is emitted only after the upstream service has verified that the S3 object exists and recorded its
content hash. The attachment identity is generated by the BFF when upload begins, and the object key is deterministic
from the user, upload, and filename. Download URLs are generated on demand as presigned GET URLs rather than persisted.
The API limits uploads to 10 MB.

Repeated create events do not duplicate the projection. `USER_UPLOAD_DELETED` removes it.

### Job listings

Job listing metadata arrives from `job-storage-service` CDC events and serves browsing, filtering, and full-text search.
A database trigger maintains the search representation whenever a listing is created or updated. Search relevance
weights the title highest, company and required skills next, and description last. This design supports text queries
without rebuilding the search document in application code; the read design also supports chronological ordering when
there is no query and company filtering.

The projection retains the upstream listing identity, monotonically increasing snapshot version, and raw-content hash.
The BFF does not enforce event ordering by version, so the last event writer wins. The raw-content hash is retained for
observability even though deduplication belongs to `job-storage-service`. Create and update events both replace the
current mutable snapshot; `JOB_LISTING_DELETED` removes it.

### Job correlations

Correlation results are projected from `job-correlation-evaluation-service`. Each result represents the score between a
search preference and a listing and supplies the frontend's ranked "My Matches" view.

The user identity is duplicated from the preference snapshot because deriving it from the preference on every read would
require another lookup. Listing title, company, URL, and location are likewise duplicated from the event's embedded
listing snapshot so a complete match card can be returned without joining the listing projection. Scoring breakdown
metadata is surfaced unchanged from the producing service. These choices support the primary per-user read, optional
filtering by preference, and score ordering.

There is one correlation per preference-listing pair. That pair is also the idempotency identity for evaluation events:
a repeated or later evaluation updates the existing result. Re-scoring after model updates or feedback incorporation
replaces the fit score, pipeline status, and score breakdown.

### Document schemas

Schema families group related JSON schemas by namespace. Their intended upstream doc-schema service is not yet fully
wired into the monorepo, so the projections are currently seeded or managed manually. Families can be deactivated
without being removed and are organized for namespace-filtered discovery.

Schema versions belong to a family and advance monotonically within it. The BFF retrieves the latest version for
presentation and uses the full JSON Schema document to validate template data before publishing
`DOC_CONTENT_GENERATION_REQUESTED`.

### Document templates

Template projections mirror Jinja2 HTML templates from `doc-template-service`. The design keeps each
namespace/name/version as a complete template version, allowing multiple versions of the same named template. The BFF
uses the projection both to display available templates and to embed the selected content in
`DOC_TEMPLATE_RENDER_REQUESTED`. Embedding the content follows the event-carried state transfer pattern, so
`doc-template-service` does not need a separate lookup when it handles the request. A template's content schema is also
retained for variable validation, and ownership is retained when required by its access policy.

`DOC_TEMPLATE_CREATED` and `DOC_TEMPLATE_UPDATED` replace the corresponding version projection idempotently.
`DOC_TEMPLATE_DELETED` hard-deletes it.

## Locally owned asynchronous request state

### Document generation

Document generation state is written directly by the BFF rather than projected from an upstream service.
`POST /api/v1/documents/generate` records the request synchronously before publishing its Kafka command. The request
identity is also placed in the event's `metadata.correlation_id`, which lets `DOC_TEMPLATE_RENDER_COMPLETED` find the
correct request. Reads are scoped to the requesting user, and the selected template version is retained for
observability.

A request follows `pending -> in_progress -> completed` or `pending -> in_progress -> failed`. Successful completion
records the rendered object's S3 key, byte count, and content hash; failure records the upstream error detail. Terminal
transitions also record their completion time.

### Command progress

Command progress records let the frontend correlate a `202 Accepted` response with later status polling. They are
created synchronously by the API immediately before `kafka_client.publish()`, using the same request identity carried in
the command's `metadata.correlation_id`. The lifecycle allows `pending -> in_progress`, `pending -> completed`, or
`pending -> failed`, followed by `in_progress -> completed` or `in_progress -> failed`.

Profile and template operations use this tracking. Upload operations and feedback commands do not, and document
generation uses its dedicated lifecycle instead. Upstream CDC events complete a tracked command when the corresponding
projection handler marks it complete.

## Delivery, idempotency, and operational meaning

Shared migration helpers provision outbox and processed-event infrastructure for the shared Kafka client library. The
BFF does not use a transactional outbox for command publishing. Because request state is recorded before the Kafka
publish, the request record still exists if publication fails; its existence alone is not proof that the command was
delivered.

Projection upserts and event-specific conflict handling make redelivery safe as described above, but they do not make
reads strongly consistent. Projection state can lag its upstream source while events are in flight. Useful operational
signals include upstream account mutation time, listing snapshot version and raw-content hash, the template version
selected for generation, correlation and request identities, async lifecycle state, terminal time, and recorded failure
detail.
